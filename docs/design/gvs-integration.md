# From pi-strata to pi-episteme: GVS-style orchestration design notes

> **Historical document.** Written before the `pi-strata` → `pi-episteme`
> rename: it refers to `pi-strata`, `strata.ts`, `strata-phase-boundary` and
> `.pi_strata/`, which are now `pi-episteme`, `episteme.ts`,
> `episteme-phase-boundary` and `.pi_episteme/`. It records the design
> reasoning behind Stage 1 (Manager → Workers → Verifier); the current
> behaviour contract is `SPEC.md`.

Теперь картина стала гораздо интереснее. Посмотрев исходники `pi-strata`, я считаю, что не нужно разрабатывать новый плагин поверх него. Лучше эволюционировать сам pi-strata в систему управления сложными задачами, взяв GVS5H (https://github.com/slee-persis/GVS5H) за основу механизма оркестрации.

У тебя уже реализована значительная часть инфраструктуры, которая необходима для такого решения.

Я бы разделил две технологии следующим образом:

- Strata отвечает за управление долговременным состоянием задачи и контекстом.
- GVS отвечает за управление процессом решения задачи посредством нескольких независимых вызовов модели.

Это два взаимодополняющих уровня.

## 1. Что уже есть в pi-strata

Я внимательно посмотрел `SPEC.md`, `index.ts`, `strata.ts` и `compaction.ts`.

Есть несколько решений, которые я бы обязательно сохранил.

1\. Послойное представление состояния

Сейчас Strata использует следующую структуру:

RESEARCH

Исследование задачи, требования, ограничения

PLAN

Исходный план со стабильными ID

MILESTONE / STEP

Отчёты выполненных этапов и архивированные результаты

PLAN-DELTA

Актуальная версия плана с изменениями

Ephemeral context

Текущая работа, вызовы инструментов, выводы команд и прочие временные данные

Особенно удачно, на мой взгляд, сделана работа с `PLAN-DELTA`: исходный план не переписывается, завершённые шаги сохраняют свои ID, а изменения записываются отдельным полным представлением актуального плана.

2\. Компактизация на границах этапов

Ты реализовал интересную механику с `strata-phase-boundary`.

После `advance` расширение создаёт sentinel, а при `agent_settled` инициирует компактизацию. В plan/step-режиме сохраняется каноническое представление Strata без обычного LLM-хвоста Pi.

При этом обычная компактизация продолжает работать отдельно, сохраняя недавний контекст и суммаризируя эфемерную работу.

Это очень хорошая основа для многократного запуска агентов с чистым контекстом.

Мне кажется, здесь особенно важно не потерять твою идею с KV-cache.

## 2. Как совместить Strata и GVS5H

Я бы не стал буквально переносить файловую структуру GVS5H в Strata.

У тебя уже есть собственное представление состояния. Лучше использовать его как основу, а файловый ledger GVS5H сделать рабочим представлением этого состояния для независимых вызовов модели.

Предлагаю следующую архитектуру:

Pi Main Agent

Взаимодействует с пользователем, принимает решение о запуске сложного режима

GVS Orchestrator

Управляет последовательностью вызовов модели и состоянием исполнения

Manager

Планирование и координация

Workers

Решение подзадач

Reviewer

Независимая оценка

Verifier

Проверка результата

Чтение и обновление состояния

Strata State

Долговременное состояние

`RESEARCH`, `PLAN`, `STEP`, `MILESTONE`, `PLAN-DELTA`

GVS Workspace

Рабочее представление

`task.md`, `notes.md`, `tasks.json`, промежуточные результаты и артефакты

Working Directory

Исходный код, файлы проекта, тесты и результаты выполнения

Ключевое решение: Strata остаётся источником долговременного состояния, а GVS Workspace представляет собой материализованное рабочее представление этого состояния.

Это важно, поскольку в текущей архитектуре pi-strata данные слоёв живут в истории разговора. Файлы в `.pi_strata/tmp/` — это восстановимые снимки контекста, а не самостоятельная база состояния.

## 3. Как будет выглядеть процесс решения задачи

Возьмём сложную задачу: реализовать новый компонент библиотеки.

Предположим, основной Pi решает, что обычного последовательного выполнения недостаточно.

Этап 1. Исследование и планирование

Manager получает исходную задачу, информацию о проекте и требования пользователя.

Он формирует:

- RESEARCH — описание задачи и технические ограничения.
- PLAN — декомпозицию на самостоятельные подзадачи.
- GVS Workspace — актуальное представление плана и рабочего состояния.

После этого Strata выполняет компактизацию.

Этап 2. Выполнение

Orchestrator выбирает очередную подзадачу.

Каждый Worker запускается с новым контекстом:

```text
System instructions
    |
Strata context
    |
Relevant task knowledge
    |
Current subtask
    |
Relevant source files
```

Worker не получает всю историю предыдущих вызовов.

Он может использовать инструменты Pi для исследования и изменения файлов. По окончании возвращает структурированный результат:

```text
{
  "task_id": "S2",
  "status": "completed",
  "changed_files": [
    "src/component.c",
    "include/component.h"
  ],
  "verification": {
    "command": "make test",
    "passed": true
  },
  "findings": [],
  "risks": []
}
```

Orchestrator проверяет результат и сохраняет отчёт в `STEP-S2`.

Этап 3. Управление знаниями

После нескольких Worker-вызовов появляется информация, которую необходимо передать следующим исполнителям.

Manager обрабатывает отчёты:

- извлекает новые факты;
- объединяет повторяющиеся выводы;
- фиксирует решения;
- выявляет противоречия;
- обновляет оставшиеся задачи.

Если план изменился, создаётся `PLAN-DELTA`.

Если отчётов стало слишком много, задействуется существующий механизм MILESTONE.

Этап 4. Верификация

Verifier запускается в независимом контексте.

Он получает исходные требования, результаты реализации, изменённые файлы и результаты тестирования.

Ему необязательно передавать рассуждения Worker. Наоборот, независимость проверки может быть полезна.

Если обнаружены проблемы, Manager создаёт корректирующие задачи.

Если всё успешно, Pi Main Agent получает итоговый результат и возвращается к пользователю.

## 4. Самое интересное: как улучшить твою модель компактизации

Я бы не ограничивался существующими слоями.

При интеграции GVS5H обнаруживается одна особенность: появляется существенное различие между информацией о задаче и информацией о процессе её решения.

Например:

| Информация                   | Хранение          |
| ---------------------------- | ----------------- |
| Требования и ограничения     | RESEARCH          |
| Стратегия решения            | PLAN              |
| Технические факты            | Notes / MILESTONE |
| Результаты подзадач          | STEP              |
| Изменения плана              | PLAN-DELTA        |
| Текущее состояние исполнения | GVS Workspace     |
| Исходный код и артефакты     | Working Directory |

Я бы пока не добавлял новый слой `NOTES` в каноническое представление Strata.

Сначала можно формировать `notes.md` из RESEARCH, STEP и MILESTONE. Это позволит избежать изменения формата слоёв и миграции существующих сессий.

При этом сам механизм MILESTONE можно использовать для более интеллектуального сжатия накопленных знаний.

В дальнейшем, если выяснится, что такой подход недостаточно эффективен, можно ввести отдельный слой для накопленных знаний с его собственными правилами обновления и компактизации.

## 5. Важный нюанс: KV-cache и независимые агенты

Здесь я вижу возможность получить дополнительное преимущество для локальных моделей.

GVS5H использует независимые экземпляры модели. Но независимый экземпляр не обязательно означает другой inference-сервер или другой процесс.

Можно использовать одну локальную модель и последовательно выполнять запросы, каждый раз создавая новый контекст.

При этом нужно внимательно спроектировать структуру промпта.

Например:

```text
[System prompt: static]
[Strata instructions: static]
[RESEARCH]
[PLAN]
[MILESTONE]
[STEP reports]
[PLAN-DELTA]

[Role-specific instructions]
[Current task]
[Relevant files]
```

Общая часть остаётся одинаковой для всех вызовов.

Специфические инструкции Worker, Reviewer или Manager располагаются после неё. Таким образом, при поддержке prefix caching сервер потенциально сможет повторно использовать значительную часть KV-cache.

Это особенно интересно для твоего сценария с локальной Qwen3.8-27B.

Но есть одна тонкость: не следует включать в общую часть изменяемые данные вроде номера итерации, времени запуска или динамического статуса. Это будет разрушать стабильность префикса.

## 6. Как бы я организовал разработку

Я предлагаю не пытаться сразу реализовать всю систему.

| Этап | Реализация          | Цель                                                   |
| ---- | ------------------- | ------------------------------------------------------ |
| 1    | GVS Orchestrator    | Несколько последовательных вызовов одной модели        |
| 2    | Context Builder     | Независимая сборка контекста каждого вызова            |
| 3    | Workspace           | Материализованный ledger из состояния Strata           |
| 4    | Manager / Worker    | Автоматическая декомпозиция и исполнение               |
| 5    | Reviewer / Verifier | Независимая проверка результатов                       |
| 6    | Adaptive Compaction | Адаптивное сжатие знаний и перераспределение контекста |

Для первого прототипа я бы сделал только Manager → Worker → Manager → Worker → Verifier.

Без параллельности. Один Worker за раз. Одна локальная модель.

Так будет гораздо легче выяснить, какой именно прирост даёт оркестрация, а какой — компактизация.

Есть ещё один технический момент: я бы реализовывал всё внутри одного расширения pi-strata, разделив код на отдельные модули. Не стоит создавать второе независимое расширение, которое также подписывается на `session_before_compact`: в Pi результаты нескольких обработчиков этого события могут перезаписывать друг друга. В твоей спецификации эта проблема уже отдельно отмечена.

## Моё основное предложение

Я бы сформулировал новую цель проекта так:

Pi-Strata — Context-Aware Agent Orchestration Framework for Local LLMs.

Не просто расширение для компактизации, а система, которая позволяет относительно небольшой модели решать сложные задачи благодаря:

1. Иерархическому сохранению знаний.
2. Контролируемой декомпозиции задач.
3. Независимым вызовам модели.
4. Динамическому формированию контекста.
5. Независимой проверке результатов.
6. Оптимизации повторного использования KV-cache.

И самое важное: эти механизмы должны работать совместно, а не независимо друг от друга.

Я бы следующим шагом занялся проектированием внутренней модели состояния и протокола взаимодействия Manager/Worker с Strata. Именно от этого решения будет зависеть, насколько органично GVS5H интегрируется в существующую реализацию и не придётся ли впоследствии переписывать её фундаментальные механизмы.
