# Техническая спецификация pi-episteme

## 1. Назначение и границы

pi-episteme — расширение Pi Coding Agent для контекстно-ориентированной оркестрации агентов с локальными LLM. Уровень 1 — послойная компактизация контекста: расширение сохраняет исследование, план и технические отчёты, а эфемерные логи удаляет на границах фаз или суммаризует при обычной компактизации. Уровень 2 — файловая-независимая оркестрация (этап 1, по мотивам GVS): последовательный пайплайн Manager → Worker → Verifier поверх независимых вызовов одной модели, состояние которого целиком живёт в слоях разговора (см. §10).

Детерминированный префикс предназначен для переиспользования KV-кэша локальными LLM (llama.cpp, Ollama и совместимыми серверами). Фактическое попадание в кэш зависит от провайдера. Оценка токенов, задержка и поля usage не считаются самостоятельным доказательством cache hit; используются только явно сообщённые провайдером метрики.

Состояние слоёв хранится в разговоре. Файлы `<session>.pi_episteme/tmp/` содержат только восстановимые сырые снапшоты и не являются источником состояния плана.

## 2. Модель контекста

```text
[Layer 0] системный промпт + статичные инструкции pi-episteme
  [RESEARCH] исследование текущей задачи
    [PLAN] базовый план
      [MILESTONE-N] дайджесты архивированных отчётов
        [STEP-ID] отчёты завершённых шагов
          [PLAN-DELTA] полный новый эффективный план
            [current] текущая работа и вывод инструментов
```

Каноническая summary начинается с `## PI-EPISTEME CONTEXT (v1)`. Блоки выводятся строго в порядке **RESEARCH → PLAN → MILESTONE → STEP → PLAN-DELTA**, нормализуются и соединяются через `\n\n`. Повторная сборка уже канонических слоёв не меняет их байты. Динамический LLM-хвост всегда находится после них.

Маркер блока:

```text
/*EPISTEME::<KEY>::v1*/
тело
/*EPISTEME::END::<KEY>::v1*/
```

Поддерживаются `RESEARCH`, `PLAN`, `PLAN-DELTA`, `MILESTONE-N` и `STEP-ID`. Незакрытые и пустые блоки игнорируются. Последний применимый блок того же ключа заменяет предыдущий.

Новым маркерам доверяют только в тексте ассистента и в каноническом префиксе предыдущей episteme-summary. Маркеры в user/tool-сообщениях не изменяют слои. Маркеры в неканоническом LLM-хвосте также не входят в доверенный префикс.

## 3. План и завершение шагов

Новый пункт плана записывается со стабильным уникальным ID:

```text
- [id:S1] Изменить src/example.ts, запустить npm test и записать результат
```

ID соответствует `[A-Za-z0-9][A-Za-z0-9_-]*`. Действие пункта должно быть самодостаточным: файлы/модули, конкретная работа, команды проверки и ожидаемый результат.

PLAN и PLAN-DELTA — плоский список: пунктом считается только маркер `-`/`*`/`+` в нулевой колонке. Вложенные подпункты и строки внутри code fence пунктами не являются; строка с отступом без маркера присоединяется к тексту предыдущего пункта. Причина жёсткая: каждый отслеживаемый пункт обязан получить STEP-отчёт, и вложенный план создал бы пункты, которые нельзя закрыть advance-ом.

Отчёт использует тот же ID: `STEP-S1`. Он содержит выполненную работу, изменённые файлы, результаты проверок, решения, риски и путь к сырому снапшоту. Прогресс вычисляется из STEP и `Completed-Steps` в MILESTONE, а не из чекбоксов.

Старые числовые `STEP-N` и планы без явных ID остаются читаемыми. Их ID выводится из позиции пункта в отфильтрованном плоском списке. Инструмент принимает как строковый ID, так и legacy numeric position; число должно быть целым и не меньше 1.

`PLAN-DELTA` содержит **полный новый эффективный план**, а не список изменений. Базовый PLAN остаётся неизменным. Завершённые пункты нельзя удалять или менять их ID/текст; новые работы получают свежие ID. Дубликаты ID и STEP без соответствующего пункта отклоняются. Шаги выполняются в порядке эффективного плана.

Новый RESEARCH начинает новый цикл: очищает PLAN, PLAN-DELTA, STEP и MILESTONE. До принятия `advance` требуется новый базовый PLAN; старый план не наследуется.

## 4. Пайплайн и фазовая компактизация

1. В strict-режиме пайплайн применяется к каждой задаче реализации. В light-режиме вопросы и небольшие задачи выполняются обычно, а пайплайн начинается только для существенной работы.
2. Модель записывает RESEARCH и PLAN, затем вызывает `episteme(action="advance")`.
3. После выполнения пункта модель записывает STEP-ID и вызывает `episteme(action="advance", step="ID")`.
4. После принятия advance расширение добавляет custom entry `episteme-phase-boundary`. Этот sentinel сохраняется в дереве сессии, но не проецируется в LLM-контекст.
5. На `agent_settled` запрашивается компактизация. В plan/step-режиме `firstKeptEntryId` указывает на sentinel, поэтому после компактизации остаётся каноническая episteme-summary без сырых логов и без LLM-хвоста pi.
6. При успешной step-компактизации сырой discarded + retained контекст сохраняется в `tmp/step_ID_raw.md`. Создание sentinel само по себе не создаёт summary или снапшот.

Публичный API pi перед `session_before_compact` выполняет model/auth preflight и подготовку компактизации. Он может отказать в компактизации малой сессии до вызова расширения. Поэтому pi-episteme не объявляет forced compaction гарантированной: ошибка переводит advance в явный **deferred/degraded mode**, pending очищается, пайплайн продолжается с полной фазой в контексте, а следующий advance повторяет попытку. Для гарантированной принудительной компактизации малой сессии требуется отдельная поддержка upstream API.

## 5. Обычная компактизация episteme-сессии

Автоматическая overflow-компактизация и `/episteme compact` вне pending-фазы используют plain-режим:

1. канонические слои извлекаются из доверенных источников;
2. `firstKeptEntryId` pi не меняется, обычный retained tail сохраняется;
3. EPISTEME-блоки структурно удаляются из assistant-сообщений, переданных стандартному суммаризатору pi;
4. предыдущий LLM-хвост отделяется от канонического префикса и участвует в обычном merge;
5. summary эфемерной работы добавляется после слоёв;
6. блок слоя, чьё точное текстовое представление остаётся в retained tail, в summary не дублируется (список — `details.episteme.dedupedWithTail`). Теряется только повторная оплата токенов: на следующей компактизации копия из хвоста извлекается и возвращается в канонические слои. Разбор канонического префикса (`previousCanonicalSummary`) допускает такое подмножество блоков.

Если LLM недоступна или суммаризация завершилась ошибкой, добавляется `PI-EPISTEME RAW CHECKPOINT`: не более последних 12 000 символов очищенного discarded-контекста. Это ограниченный fallback вместо потери незавершённой работы. Abort не маскируется и отменяет операцию.

Если несколько расширений обрабатывают `session_before_compact`, побеждает результат последнего обработчика. pi-episteme помечает свой результат через `details.episteme` и предупреждает, если сохранённая summary была заменена. Флаг «мы выдали результат» сбрасывается в начале каждого `session_before_compact`, в том числе до раннего возврата по выключенному режиму: иначе первая компактизация после `/episteme-off` выглядела бы как украденный summary.

## 6. Бюджет постоянных слоёв и MILESTONE

`layerTokenBudget` по умолчанию равен 16384 оценочным токенам. Оценка всей канонической summary — `ceil(characters / 4)`, а не tokenizer провайдера. Значение `0` отключает ротацию.

При превышении бюджета и наличии STEP-отчётов:

1. milestone-суммаризатор получает все слои, включая отчёты, и создаёт долговременный дайджест;
2. после успеха полные слои до ротации архивируются в `tmp/epoch_N_layers.md` — и только там: файл про эпоху, которой не случилось, вводил бы в заблуждение;
3. добавляется MILESTONE-N с полным списком `Completed-Steps`;
4. индивидуальные STEP-отчёты удаляются из активных слоёв только после успешной суммаризации.

При ошибке milestone-суммаризации отчёты сохраняются полностью. Архивированные ID продолжают участвовать в прогрессе, разблокировке следующих шагов и проверке неизменности завершённых пунктов.

## 7. Режимы, автопродолжение и UI

Режим является сессионным состоянием и по умолчанию выключен. Новая, возобновлённая и перезагруженная сессия начинается с off; исторические `piEpisteme.enabled` и `PI_EPISTEME_ENABLED` игнорируются.

- `/episteme-on [strict|light]` включает режим; по умолчанию light. Повторный запуск с другим режимом переключает его без off; тот же режим идемпотентен. При этом standing instructions в очереди (injected message) заменяются сообщением-superseder; в системном промпте новый режим подхватывается со следующего хода.
- `/episteme-off` выключает режим, очищает pending и отправляет отзыв standing instructions. Далее используется обычная компактизация pi, а `advance` отклоняется.
- `/episteme pause` приостанавливает только автопродолжение.
- `/episteme resume` возобновляет его и в простое ставит следующий пункт в очередь.
- `/episteme` показывает статус; `/episteme compact` запрашивает ручную компактизацию; `/episteme abort` (`cancel`) прерывает выполняющуюся оркестрацию; `/episteme reset` после подтверждения удаляет сырые снапшоты. Неизвестная подкоманда сопровождается предупреждением, статус при этом всё равно показывается; `reset` в headless явно сообщает, что требуется интерактивный UI (он подтверждает удаление).

При включении в непустой сессии инструкции сначала отправляются custom message в конец контекста, чтобы не менять системный префикс. После следующей компактизации они переносятся в системный промпт. В пустой сессии системный промпт обновляется сразу.

После завершения или deferred-ошибки advance `autoContinue` ставит следующий незавершённый пункт в очередь, если режим не поставлен на паузу.

TUI показывает либо прогресс эффективного плана, либо strict/light/off/paused. Маркеры скрываются только при отображении. Статус содержит оценку размера слоёв, бюджет, epoch, счётчики успешных/deferred-компактизаций и последние provider-reported `cacheRead/input`.

## 8. Конфигурация

Приоритет каждого поля: environment → project settings → global settings → default. Невалидное значение игнорируется, после чего применяется следующий источник.

| Environment | `piEpisteme` в settings.json | Default |
| --- | --- | --- |
| `PI_EPISTEME_AUTO_CONTINUE` | `autoContinue` | `true` |
| `PI_EPISTEME_HIDE_ANCHORS` | `hideAnchors` | `true` |
| `PI_EPISTEME_LAYER_TOKEN_BUDGET` | `layerTokenBudget` | `16384` |
| `PI_EPISTEME_ORCH_FIX_ROUNDS` | — (env-only) | `2` |

Boolean env принимает без учёта регистра `1/true/on` и `0/false/off`. Бюджет должен быть неотрицательным целым. Файлы: `~/.pi/agent/settings.json` и `<project>/.pi/settings.json`.

## 9. Оркестрация (этап 1, GVS-style)

Запуск: действие `orchestrate` инструмента `episteme` (параметр `task`) или команда `/episteme-orchestrate <задача>`. Как и `advance`, оркестрация требует включённого режима сессии: с выключенным режимом она отклоняется, потому что её слои всё равно не имел бы кто складывать при компактизации. Одновременно выполняется не более одной оркестрации на сессию расширения.

Пайплайн последовательный, без параллельности, одна модель:

1. **Manager** (chat-only вызов через `ModelRegistry.complete`): формирует RESEARCH и базовый PLAN в маркерах Episteme. Невалидный результат (нет блоков, нет пунктов, дубликаты ID) один раз возвращается Manager с текстом ошибки; повторная неудача завершает прогон с `ok=false`.
2. **Worker** (независимая in-memory сессия агента на каждый пункт): создаётся через `createAgentSession` с `noExtensions/noSkills/noPromptTemplates/noThemes`, стандартными coding-tools, моделью и thinking level вызывающей сессии. Файлы контекста проекта (`AGENTS.md`) загружаются: worker правит репозиторий и обязан видеть его соглашения; они идентичны для всех ролей, поэтому стабильность префикса не нарушается. Worker получает чистый контекст и выполняет строго один пункт плана по порядку эффективного плана. Финальное сообщение парсится на блок STEP-ID; без маркера всё финальное сообщение сохраняется как отчёт (работа не теряется).

   **Согласование инструментов worker'ов.** В pi право на выполнение инструмента — обработчик `tool_call` расширения, поэтому `noExtensions` лишил бы worker'ов и пользовательской политики согласования. Оркестратор возвращает ровно эту функцию inline-расширением `pi-episteme-worker-approval`: вызовы вне списка read-only (`read/grep/glob/ls/find/search/webfetch`) подтверждаются через UI родительской сессии с вариантами «один раз», «все на этот прогон», «заблокировать»; блокировка возвращает `{ block: true }`. В headless-режиме спросить некого: режим фиксируется однократным предупреждением, а не молчаливым автоподтверждением.
3. **Verifier** (независимая сессия агента с инструментами): сам запускает команды проверки из пунктов плана и отвечает одним JSON-объектом `{"verdict":"pass"|"fail","issues":[…],"summary":"…"}`. Неразбираемый ответ трактуется как `fail` (fail-closed).
4. При `fail` Manager получает список issues и выпускает `PLAN-DELTA` — полный новый эффективный план. Дельта валидируется `planChangeError` и `planIdError`, после чего **сливается в существующие слои** (меняется только `planDelta`); замена слоёв запрещена, чтобы завершённые пункты не выполнялись повторно. Число корректирующих раундов ограничено `PI_EPISTEME_ORCH_FIX_ROUNDS` (по умолчанию 2, жёсткий потолок `MAX_FIX_ROUNDS` = 10: каждый раунд повторно выполняет незакрытые пункты в реальном рабочем дереве), после чего прогон завершается с `ok=false` и открытыми issues.

**Файлы не используются:** состояние прогона — это набор слоёв Episteme в памяти оркестратора. По завершении в очередь основной сессии ставится пользовательское сообщение с просьбой перевыпустить канонические блоки от имени ассистента — только текст ассистента является доверенным источником для извлечения слоёв и переживания компактизацию.

**Контракт стабильности префикса (KV-cache):** системный промпт каждого вызова прогона равен `[ORCHESTRATION_HEADER] + \n\n + [каноническое summary слоёв]` и собирается только из статичного заголовка и значений слоёв. Ролевые инструкции, текущий пункт, issues и любые изменяемые данные размещаются исключительно в пользовательском сообщении после префикса. Неизменные слои обязаны давать побайтово идентичный префикс (покрыто offline-тестами).

**Прерывание:** оркестрация принимает `AbortSignal`; abort пробрасывается в chat-only вызовы (опция `signal`) и во вложенные сессии агентов (`session.abort()` по сигналу). Командный обработчик pi не получает сигнал операции, поэтому прогон владеет собственным `AbortController`: им управляют `/episteme abort` и `session_shutdown`; сигнал отмены инструмента (если он есть) перенаправляется в этот контроллер.

**Отмена компактизации:** если pi отклоняет компактизацию признаком отмены (`AbortError` или сообщение `Compaction cancelled` — типизированного маркера в pi нет), ожидающая фаза НЕ сбрасывается: `phase-boundary` остаётся и повторится на следующем `agent_settled`. Жёсткая ошибка (например «session too small») по-прежнему снимает pending, чтобы запрос не висел вечно.

## 10. Проверка

```bash
npm test
npm run typecheck
npm run test:local
```

Offline self-test покрывает протокол, команды, fallback, rollover, мост согласования инструментов worker'ов, гейт оркестрации по режиму, дедупликацию слоёв с retained tail и реальные публичные `buildContextEntries`/`buildSessionContext` pi для sentinel. Тот же набор (`npm run typecheck` + `npm test`) выполняет CI на Node 22.19/22/24 (`.github/workflows/ci.yml`). `test:local` требует `PI_EPISTEME_TEST_URL` и `PI_EPISTEME_TEST_MODEL`; `PI_EPISTEME_TEST_API_KEY` необязателен. Без endpoint проверка завершается со `SKIP`. Cache read сообщается только при явной положительной cached-token метрике провайдера.
